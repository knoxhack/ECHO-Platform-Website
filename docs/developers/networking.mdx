## Role

Networking connects player actions, server state, UI updates, and synchronized gameplay systems. ECHO networking should prioritize safety, clear ownership, and debuggable behavior.

NetCore is the expected home for shared networking patterns. Individual modules can define actions and payloads, but they should follow the same rules for authority, validation, rate limiting, and diagnostics.

## When to Use Networking

Use networking when a module needs to:

- Send a player action from UI to server authority.
- Synchronize mission, scan, map, or unlock state.
- Notify a client that data changed.
- Request a server-owned calculation.
- Confirm that an interaction is allowed.

Do not use networking to bypass service contracts. A packet should usually call into a service that owns the behavior.

## Packet and Action Checklist

Every networked action should describe:

- Packet or action ID.
- Direction of travel.
- Owning module.
- Required permission or progression state.
- Server authority rules.
- Rate-limit expectations.
- Validation failures.
- Debug log fields.
- Compatibility or migration concerns.

## Server Authority

Player-facing UI can request actions, but gameplay state should be owned by the authoritative side. A Terminal button, Lens scan, or HoloMap action should not blindly mutate world state without server-side validation.

Example action handler shape:

```ts
netCore.actions.register({
  id: "echoterminal.claim-reward",
  direction: "client-to-server",
  rateLimit: "player:2s",

  validate(request, context) {
    return context.services.missions.canClaimReward({
      playerId: request.playerId,
      missionId: request.payload.missionId,
      rewardId: request.payload.rewardId
    });
  },

  handle(request, context) {
    return context.services.missions.claimReward({
      playerId: request.playerId,
      missionId: request.payload.missionId,
      rewardId: request.payload.rewardId
    });
  }
});
```

The example is intentionally service-first. The packet validates and routes the action; MissionCore owns reward behavior.

## Safety Rules

Validate inputs before applying changes.

Rate-limit actions that can be triggered repeatedly.

Avoid sending large payloads when an identifier or compact state update is enough.

Treat missing providers, stale IDs, and unloaded world state as normal failure modes that need clear handling.

Use explicit failure states:

- `invalid-payload`
- `missing-provider`
- `not-unlocked`
- `target-unloaded`
- `rate-limited`
- `unsupported-runtime`

## Sync Patterns

Prefer small, owned updates:

```ts
netCore.sync.publish("echolens.scan-state", {
  playerId,
  targetId,
  scanState: "known",
  relatedIndexEntry: "relictech.ancient-capacitor"
});
```

Avoid dumping full world state into a UI packet. Terminal, Index, Lens, and HoloMap should receive the data they need, not every internal field a module happens to store.

## Debugging

Networking code should make support easier. Useful logs include:

- Packet or action ID.
- Direction.
- Player.
- Target system.
- Validation result.
- Failure reason.
- Runtime adapter.
- Module version.

Avoid logging sensitive or excessive data. Logs should help reproduce a problem, not expose private state.

## Common Mistakes

- Trusting client UI state as proof that an action is allowed.
- Sending large payloads when an ID and version would work.
- Mutating save data directly from packet code.
- Retrying failed actions without a rate limit.
- Hiding errors that should become launcher, support, or diagnostics signals.
