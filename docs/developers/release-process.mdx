## Purpose

The release process connects developer outputs to player-ready launcher packages. It should become increasingly PackOS-aware over time.

The goal is not only to produce files. The goal is to produce an installable, repairable, documented, and validated official ECHO experience. Today, that means a Minecraft/NeoForge-compatible player path through ECHO Launcher. Future native runtime work should remain clearly marked as future-facing unless a specific feature has shipped.

## Release Inputs

A release should eventually include:

- Module builds.
- Experience metadata.
- PackOS manifest.
- Lockfile.
- Release channel.
- Version notes.
- Dependency list.
- Checksums or integrity data.
- Launcher download metadata.
- Known issues.
- Troubleshooting path.
- Docs links for changed systems.

## Example Release Metadata

The shape below is illustrative until PackOS and SDK formats are formally locked.

```json
{
  "experience": "ashfall",
  "version": "1.0.1",
  "channel": "public",
  "runtime": {
    "target": "minecraft-neoforge",
    "adapter": "echoadaptercore"
  },
  "artifacts": [
    {
      "kind": "echo-pack",
      "file": "ashfall-1.0.1.echo-pack.zip",
      "sha256": "..."
    },
    {
      "kind": "packos-manifest",
      "file": "ashfall-1.0.1.pack.json",
      "sha256": "..."
    }
  ],
  "modules": ["echocore", "echoterminal", "echolens", "echoholomap"],
  "knownIssues": ["Launcher installers are published separately when available."]
}
```

The release metadata should help the launcher and download portal tell the truth about what exists. If Windows or Linux installer assets are not published, the site should not imply that they are.

## Validation Gates

Useful release gates include:

- Required metadata exists.
- Dependencies resolve.
- Versions are compatible.
- No planned-only module is marked stable.
- Runtime target is clear.
- Launcher assets exist when direct installer buttons are shown.
- Docs links are not broken.
- Release notes are present.
- Checksums exist for downloadable artifacts.
- Known issues are written for players and testers.

Example gate shape:

```ts
releaseGates.register({
  id: "packos.required-metadata",
  severity: "blocker",
  validate(release) {
    return release.experience && release.version && release.channel
      ? pass()
      : fail("Release is missing experience, version, or channel metadata.");
  }
});
```

Validation should fail loudly for missing release truth. A quiet failure becomes a support problem later.

## Player Readiness

Before a release is public, ask:

- Can a player install it through ECHO Launcher?
- Can the launcher repair it?
- Is the runtime target clear?
- Is there a known troubleshooting path?
- Are the release notes understandable?
- Are manual assets clearly marked as advanced?
- Do docs explain the changed systems?

Players should not need to understand module jars, manifests, or lockfiles just to play. Advanced assets can exist, but the primary path should stay launcher-first.

## Developer Readiness

Before a release is promoted, ask:

- Did every changed module update release notes?
- Did dependencies change?
- Did any save data require migration?
- Did packet or action IDs change?
- Did UI provider IDs change?
- Did PackOS metadata describe the new state?
- Did docs links still resolve?

This connects release work to [Module Template](/docs/developers/module-template), [Data Storage](/docs/developers/data-storage), and [Networking](/docs/developers/networking).

## Current Status

Some release data may remain manual until PackOS and release integration are complete. Keep the structure ready now so the workflow can become automated later.

The website currently reads GitHub release data at build time for `/download` and generated release news posts. That makes release metadata visible, but it does not replace PackOS validation.

## Common Mistakes

- Publishing files without a clear player path.
- Treating advanced assets as normal install instructions.
- Forgetting known issues because the build passed.
- Shipping module changes without docs or release notes.
- Marking future native runtime work as released before it is actually available.
